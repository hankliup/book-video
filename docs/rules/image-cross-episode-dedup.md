# 跨期去重的单一口径：pexels_index.py

- **opt-in** delivery gate (`check-episode-delivery.py --verify-photos`) because it needs the network, and it reports 未能证明 rather than 不符 when it cannot get the rendition it asked for. **The rendition is now part of the record, not an assumption:** the CDN's `w=1600` and `w=1280` are two *renderings of the same master*, and `crop_3x4()` LANCZOS-resizes each of them to 1024x1365, so their pixels differ — `fetch-pexels-by-id.py`'s width ladder lands on 1280 whenever curl 18 (transfer closed) breaks a 1600 request, and that was invisible to the verifier, which always asked 1600. 《猎人笔记》 2026-10-06 `atmosphere-5` (Pexels #32176786) was fetched at 1280, replayed at 1600, and reddened as 不符 (mean 5.0, peak 71) while the identical replay at 1280 measured **mean 0.000 / peak 0 / overshoot 0.000%** (and at 1024: 10.80 / 136). A false red of that shape sends a person to replace a photograph that has nothing wrong with it, and the cost is a whole body set re-fetched, re-graded, re-rendered. So `certify()` writes `source_width` — the **actual pixel width of the source that landed**, not the rung requested — into `_provenance.json`, and `verify-pexels-fetch.py`'s `replay_width()` resolves the rung in three steps (marker's `source_width` → the `_original/<name>.png` width for pre-2026-10-06 markers → default 1600), refuses to compare at all when the resolved width is below `TARGET_W` (a crop from there is an upscale, so it proves nothing), and reports 未能证明 — never 不符 — when the CDN returns a width other than the one recorded. `scripts/tests/test-replay-width.py` runs the real `main()` against a stubbed CDN and asserts all three directions (same rung + same photo green, same rung + different photo red 「不符」, same photo + different rendition red 「未能证明」 and its output must not contain 不符), plus that the rendition-vs-rung gap itself is >3× `MEAN_TOL` so the test cannot go vacuous; `npm run check` runs it and statically guards that the test still names `replay_width`, `source_width`, `fetch_bytes` and both script filenames. Do not substitute a perceptual hash for the marker chain: measured on this very set, the *same* photograph raw-vs-graded scores dHash distance up to 31 while two *different* photographs score as low as 12, so once grading is in-place a hash cannot prove "this file is that photo" — the checkable chain is manifest id → `_provenance.json` → `_raw` sha256 → graded still → delivered frame (`scripts/check-hook-frame-match.py`), and `npm run check` statically guards that the marker is written *and* read, that one `crop_3x4()` serves both fetcher and verifier, and that the exists-skip still goes through `certified_existing()`. A marker is demanded only in an image directory that already carries one, so the delivered legacy episodes stay out of the blast radius instead of turning this into a hundred-episode dig. Cross-*episode* duplicates used to stay outside every gate — the same photograph could sit in one episode's body and another's hook and nothing in the repo could see it, because every check only ever opened one episode.
